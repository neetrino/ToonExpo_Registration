## 1. Objective

The integration must provide:

- ticket sales and registration on both parties' websites;
- immediate availability of Toon Expo tickets in Mootq so they can be validated by Mootq scanners right away;
- transfer of Mootq registrations to Toon Expo for shared reporting (nightly is acceptable);
- preservation of the same ticket code in both systems;
- transfer of answers to registration questions in one `answers` object;
- preservation of the language in which the visitor completed the form;
- no continuous API polling and no WebSocket.

The primary exchange is one idempotent `POST` per registration. List/cursor polling and a full dataset dump are not v1 partner obligations.

## 2. Ticket and Code Ownership

The code is generated by the system in which the user registered:

- registration in Mootq → Mootq generates the code;
- registration in Toon Expo → Toon Expo generates the code.

The receiving party must store the code unchanged. It does not generate a new code or replace the received one.

### 2.1 Code Format

Confirmed for launch (case-sensitive, uppercase only):

```text
^(MQ|TE)[A-Z0-9]{11}$
```

Examples:

```text
MQ7K4M2X9P3R8
TE8D6N4T7C2X9
```

Rules:

- character case is significant; both parties use uppercase;
- the code must be unique in both systems;
- if a local collision occurs, the generator creates a new code;
- the QR contains only `ticketCode`, with no URL, personal data, or access tokens;
- the scanner sends the received code to Mootq unchanged.

The prefix helps separate the code namespaces. The source is also verified through the authenticated integration channel.

## 3. Authentication and Source Identification

Each party issues the other party a separate integration credential for the relevant environment.

```http
Authorization: Bearer <integration-token>
Content-Type: application/json
Accept: application/json
```

The credential identifies:

- the calling system;
- the Toon Expo integration;
- the permitted environment;
- one specific event.

Therefore `sourceSystem` is not included in the JSON. The receiver identifies the source from the credential and verifies that the `MQ` or `TE` prefix matches the sender.

The credential is not exposed to the frontend and is not used from a browser. All integration requests are server-to-server.

Each registration credential is bound to exactly one event. A new credential is issued for every new event. One credential must not be reused across multiple events, so `eventId` is not needed in the body.

## 4. Identifier and Idempotency

The integration uses two stable identifiers:

- `sourceRegistrationId` — the immutable registration ID in the source system and the transport idempotency key;
- `ticketCode` — the required globally unique ticket code used in the QR and for scanning.

ID transport depends on the direction:

| Direction | ID transport |
| --- | --- |
| Toon Expo → Mootq | Header `Idempotency-Key: <sourceRegistrationId>` only; `sourceRegistrationId` is prohibited in the body |
| Mootq → Toon Expo | Body field `sourceRegistrationId`; no duplicate header is required |

For a repeated request:

- same transport idempotency key, same `ticketCode`, and same data → successful replay without creating a duplicate;
- same transport idempotency key but a different payload or `ticketCode` → `409 Conflict`;
- same `ticketCode` already bound to another registration → `409 Conflict`;
- new transport idempotency key and new `ticketCode` → new registration.

If ticket reissue or mutable codes are introduced in the future, this rule must be reviewed.

## 5. Toon Expo → Mootq: Immediate Registration

After a successful registration on the Toon Expo website, the Toon Expo backend sends the ticket to Mootq immediately (after the visitor response is committed). The visitor does not wait for Mootq.

```http
POST /api/v1/integrations/toon-expo/registrations
Authorization: Bearer <toon-expo-integration-token>
Idempotency-Key: <sourceRegistrationId>
Content-Type: application/json
Accept: application/json
```

Mootq provides the full production and non-production URLs. The path above is the Mootq draft path.

Example:

```json
{
  "ticketCode": "TE8D6N4T7C2X9",
  "registeredAt": "2026-07-27T10:15:00.000Z",
  "firstName": "Example",
  "lastName": "Visitor",
  "email": "visitor@example.com",
  "phone": "+37400000000",
  "locale": "hy",
  "answers": {
    "form_version": "2026-vis-reg-v1",
    "age_band": "25-34",
    "visit_purpose": "investment",
    "investment_property_type": "apartment",
    "investment_market": "armenia",
    "investment_goal": "rental_income",
    "investment_timeline": "3_months",
    "investment_budget_usd": "100k-250k",
    "prior_investment_experience": "no_first",
    "newsletter": true
  },
  "utmSource": "facebook",
  "utmMedium": "video",
  "utmCampaign": "tey26"
}
```

`utmSource`, `utmMedium`, and `utmCampaign` are omitted when not captured. They are never sent as JSON `null`.

`sourceRegistrationId` and `sourceSystem` must not appear in this body.

### 5.1 Fields

| Field / header | Required | Description |
| --- | --- | --- |
| Header `Idempotency-Key` | yes | Stable Toon Expo registration ID; not duplicated in the body |
| `ticketCode` | yes | `TE` + 11 uppercase `A-Z0-9` |
| `registeredAt` | yes | Registration time in UTC, ISO-8601 |
| `firstName` | yes | Visitor's first name |
| `lastName` | yes | Visitor's last name |
| `email` | yes | Visitor's email |
| `phone` | yes | Phone number, preferably E.164 |
| `locale` | yes | Visitor form language: `hy`, `en`, or `ru` |
| `answers` | no | Flattened answers; see Appendix A. Omit the object when empty |
| `utmSource` | no | Landing `utm_source` when captured |
| `utmMedium` | no | Landing `utm_medium` when captured |
| `utmCampaign` | no | Landing `utm_campaign` when captured |

Mootq must accept the request when optional UTM keys are present or absent. Unknown optional top-level keys must not cause `400` / `422`.

### 5.2 Scanner Readiness Condition

Mootq returns success only after the registration and the received `ticketCode` are stored and available to ticket validation.

After `204 No Content`, the ticket must be accepted by Mootq scanners without waiting for cron, nightly synchronization, or cursor polling.

Sending email, SMS, and other external notifications must not delay this response.

Toon Expo treats any `2xx` as successful delivery and stops retrying that outbox row. Mootq should return `204`.

### 5.3 Toon Expo Responsibilities

Toon Expo:

1. stores the registration and code in its own system;
2. creates a transactional outbox record or an equivalent guaranteed task;
3. queues the delivery task immediately after commit;
4. retries temporary failures;
5. does not wait for nightly cron for the first delivery attempt;
6. retains undelivered tasks until delivery is confirmed;
7. limits delivery to Mootq to a maximum of five requests per second for one integration credential.

User registration on Toon Expo must not depend on temporary Mootq availability. If Mootq is temporarily unavailable, the user still receives the Toon Expo ticket while the backend continues retrying delivery.

```text
maximum 5 requests per second
```

If registrations are created faster, Toon Expo keeps them in the outbox and drains the queue at this rate. Mootq may return `429` when the limit is exceeded; Toon Expo retries later with backoff.

## 6. Mootq → Toon Expo: Registration Delivery

Mootq does not send a request to Toon Expo during user registration and does not create immediate outbound network traffic on this path.

A nightly scheduler selects registrations that have not yet been sent in controlled batches and creates a separate queue job for each registration. One job sends one registration to Toon Expo.

```http
POST https://reg.toonexpo.com/api/v1/integrations/mootq/registrations
Authorization: Bearer <mootq-integration-token>
Content-Type: application/json
Accept: application/json
```

Toon Expo will provide the matching non-production URL with the credential. The token is issued by Toon Expo, is bound to one event, and has write scope.

The request body uses the same contract, but `ticketCode` starts with `MQ`, and `sourceRegistrationId` is required in the body.

```json
{
  "sourceRegistrationId": "mq-98231",
  "ticketCode": "MQ7K4M2X9P3R8",
  "registeredAt": "2026-07-27T10:15:30.000Z",
  "firstName": "Example",
  "lastName": "Visitor",
  "email": "visitor@example.com",
  "phone": "+37400000000",
  "locale": "hy",
  "answers": {
    "company": "Example LLC",
    "job_title": "Founder"
  }
}
```

| Field | Required | Description |
| --- | --- | --- |
| `sourceRegistrationId` | yes | Stable Mootq registration ID; transport idempotency key |
| `ticketCode` | yes | `MQ` + 11 uppercase `A-Z0-9` |
| `registeredAt` | yes | Original registration time in UTC, ISO-8601 |
| `firstName` | yes | Visitor's first name |
| `lastName` | yes | Visitor's last name |
| `email` | yes | Visitor's email |
| `phone` | yes | Phone number, preferably E.164 |
| `locale` | yes | Visitor form language: `hy`, `en`, or `ru` |
| `answers` | no | Mootq question keys; unknown keys must not prevent storage |

Do not send `sourceSystem`. Toon Expo assigns `MOOTQ` from the credential.

Delivery rules:

- user registration in Mootq does not wait for Toon Expo and does not call the Toon Expo API;
- the nightly scheduler selects records using an indexed `not sent` marker;
- records are selected in bounded batches;
- a separate idempotent job is created for every record;
- temporarily failed jobs retry with backoff;
- successful delivery is recorded only after a successful Toon Expo HTTP response (`204`);
- the original `registeredAt` is preserved.

The delay before Mootq registrations appear in Toon Expo reports, until the next nightly run, is accepted for v1.

Toon Expo stores the record for reporting. It does not send email, SMS, or a second QR to that visitor.

## 7. Dynamic Registration Questions

Additional answers are sent in the `answers` object. The integration must not add a separate JSON field for every new question.

### 7.1 Question Key

The key is a stable technical code:

```text
^[a-z][a-z0-9_]{0,63}$
```

The key is not the displayed question text. It does not change when a translation changes. UI translations live in each system. The receiver uses the registration `locale` to pick labels.

Toon Expo → Mootq uses the catalog in Appendix A (`form_version`: `2026-vis-reg-v1`).

Mootq → Toon Expo may use Mootq's own keys. Toon Expo will store unknown keys for later mapping and will still accept the ticket.

A new required question must be agreed by both parties before it becomes required.

### 7.2 Values

Allowed value types:

- `string`;
- `number`;
- `boolean`;
- `null`;
- an array of strings or numbers for multi-select.

Nested objects are not used as a single answer value. Toon Expo flattens its internal `locationSeek` object into the keys in Appendix A.

The service fields `ticketCode`, `registeredAt`, `firstName`, `lastName`, `email`, `phone`, and `locale` are not duplicated inside `answers`. The `Idempotency-Key` header value is also not duplicated in the Toon Expo → Mootq body.

A new or temporarily unknown additional-question key must not prevent the base ticket from being stored or accepted by a scanner.

Select/radio/checkbox values are sent as stable option codes, not localized labels. Free-text values are stored exactly as entered.

## 8. HTTP Responses

| Status | Meaning |
| --- | --- |
| `204` | New record stored or identical replay processed successfully |
| `400` / `422` | Invalid structure or required data |
| `401` / `403` | Credential or access failure |
| `409` | The transport idempotency key or code conflicts with another record, or the prefix does not match the sender |
| `429` | Temporary rate limit; retry later |
| `500` / `503` | Temporary receiver failure; retry later |

Retry rules:

- network timeout, `429`, `500`, `503` → retry with increasing delay;
- `400`, `401`, `403`, `409`, `422` → automatic infinite retries are prohibited; diagnosis is required;
- no response after sending is treated as an unknown result, so the sender repeats the same `ticketCode` and the same transport idempotency key;
- the receiver must support at-least-once delivery without duplicates.

## 9. Language

The `locale` field is required in every registration body:

```json
{
  "locale": "hy"
}
```

Allowed values: `hy` | `en` | `ru`.

A missing or unsupported `locale` is a validation error (`400` or `422`).

```http
Accept-Language: ru
```

`Accept-Language` may be used only to select the language of a human-readable API error message. It does not replace `locale`.

## 10. Ticket Delivery to the Visitor

The system in which the visitor registered is responsible for the initial delivery of the ticket and QR:

- Mootq delivers tickets created in Mootq;
- Toon Expo delivers tickets created in Toon Expo.

The receiving party must not automatically send a second ticket or generate another QR.

## 11. Scanning and Attendance

Mootq is the source of truth for scanner access:

- Mootq scanners accept `MQ...` and `TE...` codes;
- a successful entry is recorded in Mootq;
- the minimum shared attendance status is `NOT_VISITED` or `VISITED`;
- detailed per-scan history is not included.

**v1:** Mootq does not send attendance-status changes to Toon Expo. Toon Expo does not change attendance status in Mootq. A later attendance POST may be agreed separately.

## 12. Recovery and Reconciliation

The primary exchange does not use:

- polling every few seconds;
- a mandatory cursor feed;
- a mandatory full-dataset export;
- WebSocket;
- a manual “event mode” switch.

The primary reliability mechanism is:

1. storing the original registration;
2. a guaranteed outbound job;
3. an idempotent `POST`;
4. retries for temporary failures;
5. a nightly check for unsent and failed jobs.

A one-time export after the event or a manual full reconciliation may be added later if it is genuinely needed. Neither replaces immediate Toon Expo → Mootq delivery.

Toon Expo may keep internal recovery tools. They are not Mootq v1 obligations.

## 13. Security

- HTTPS only;
- separate credentials for development and production, and a separate registration credential for every event;
- credentials are stored only on the backend;
- credentials can be revoked and replaced;
- the QR contains no PII or secrets;
- logs do not contain bearer tokens or the complete personal payload;
- safe technical data is logged for each request: party, `ticketCode`, time, HTTP status, attempt number, and correlation ID;
- Toon Expo limits pushes to Mootq to a maximum of five requests per second for one integration credential; overflow is queued and retried after `429`.

## 14. Information Required from Each Party

### Toon Expo Provides to Mootq

- production URL for receiving Mootq registrations: `https://reg.toonexpo.com/api/v1/integrations/mootq/registrations`;
- matching non-production URL;
- a write credential for Mootq, one per event;
- the `answers` catalog in Appendix A;
- a technical contact for integration errors.

### Mootq Provides to Toon Expo

- production and non-production URLs for immediate Toon Expo → Mootq registration delivery;
- a credential for Toon Expo, one per event;
- confirmation of the 5 requests/second limit and retry/`429` behavior;
- Mootq inbound `answers` keys if they differ from Appendix A;
- a technical contact for integration errors.

Attendance endpoint is not required for v1.

## Appendix B — Out of v1 (not required from Mootq)

- Cursor / incremental GET feed.
- Paginated full export or full import APIs.
- Attendance-status POST to Toon Expo.
- WebSocket or any persistent connection.
- Email or SMS from Toon Expo to Mootq-origin visitors.
